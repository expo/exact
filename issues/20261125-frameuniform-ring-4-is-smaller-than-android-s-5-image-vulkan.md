# FrameUniform::RING (4) is smaller than Android's 5-image Vulkan swapchain (and unsynchronized across Scratch retries), causing a CPU-GPU uniform data race

**Status:** Open
**Systems:** gpu / Vulkan (Android) & Metal
**Author:** Gemini 4 Neon
**Date:** 2026-11-25
**Severity:** P1
**Related:** LLP 1184 (Two sources of truth)

Verification: verified by reading.

At `9c0431fd5`, `gpu/src/lib.rs:635` sets `FRAME_LATENCY = 4` on Android, and both `Module::create` (`gpu/src/target.rs:65`) and `Module::attach` (`gpu/src/target.rs:128`) assign `config.desired_maximum_frame_latency = FRAME_LATENCY`. In `vendor/wgpu-hal/src/vulkan/swapchain/native.rs:171, 214, 279-285`, Vulkan maps that to `min_image_count(config.maximum_frame_latency + 1)` (>= 5 swapchain images) with `images.len()` acquire semaphores, and `NativeSwapchain::acquire` (`native.rs:484-488, 543, 720-723`) only waits on a prior submission fence when `next_acquire_index` wraps around after `images.len()` (>= 5) acquires. However, `FrameUniform::RING` is hardcoded to `4` (`gpu/src/uniform.rs:38`), and `FrameUniform::write` (`gpu/src/uniform.rs:84-105`) wraps `self.next = (self.next + 1) % self.slots.len()` and executes `unsafe { std::ptr::copy_nonoverlapping(bytes.as_ptr(), p.as_ptr(), bytes.len()) }` directly into persistently mapped `HOST_COHERENT` Vulkan memory (`gpu/src/uniform.rs:154-213`). Separately, in `Module::render` (`gpu/src/frame.rs:234-236, 289-356`), when a surface returns `frame_presentable() == false`, the single swapchain drawable is held (`inst.held = Some(texture)`) and retries render into `Scratch` and submit on `Module::flush` without acquiring a new drawable or waiting on a GPU fence.

**Triggering sequence.** On Android, `host/android/canvas/src/main/java/dev/exact/canvas/Natives.kt:167-171, 1073-1145` attaches full-window opaque canvases via `SurfaceView` (and falls back to `TextureView` when hardware buffers are refused), calling `gpu_attach` (`host/painted/src/surfaces/android.rs:276-282`) -> `Module::attach` (`gpu/src/target.rs:128`) with a Vulkan swapchain of >= 5 images. Rendering 5 consecutive animated frames of any `FrameUniform` surface (`apps/weatherlight/gpu/src/lib.rs:155`, `apps/caltrain/gpu/src/{aurora,glass,stack}.rs`) submits frames 0..3 using uniform slots 0..3 and acquire semaphores 0..3; frame 4 acquires semaphore 4 (never waiting for frame 0's submission fence) and writes slot `(3 + 1) % 4 = 0`. In steady state, frame `k + 4` waits only on frame `k - 1` (semaphore `(k + 4) % 5`) while overwriting slot `k % 4`, which frame `k` may still be reading on the GPU. Independently, any custom `Surface` calling `FrameUniform::write` across 4+ consecutive `frame_presentable() == false` `Scratch` retries on Metal or Vulkan wraps slot 0 with zero GPU synchronization (existing `packages/shader/rust/src/lib.rs:256-293` avoids this only because it skips `FrameUniform::write` while `!drawable`).

**Actual vs. expected.** `FrameUniform::write` races the GPU on persistently mapped `HOST_COHERENT` uniform memory (corrupting uniform values or violating Vulkan host-write/device-read synchronization), contradicting its own safety invariant in `gpu/src/uniform.rs:9-11, 95-98` ("a canvas holds at most three drawables, so the slot a frame writes was last read by a frame whose drawable has since been returned, its commands complete"). Because Vulkan drivers may also allocate more than `min_image_count` swapchain images, the ring must never assume a fixed count of 3 in-flight frames.

**Verification and siblings.** Verified by reading the complete Android `SurfaceView`/`TextureView` -> `gpu_attach` -> `Module::attach` -> `wgpu-core` `maximum_frame_latency` clamp -> `wgpu-hal` `NativeSwapchain::create_swapchain`/`acquire` -> `FrameUniform::write` path. Siblings checked: `gpu/src/buffers.rs:32` (`IN_FLIGHT = 3`, gated by `on_submitted_work_done` in `gpu/src/frame.rs:398-415`) stays strictly below `RING = 4`; `gpu/src/window.rs:84` uses latency `2`; Metal `vendor/wgpu-hal/src/metal/surface.rs:336` sets `maximumDrawableCount = 3` (`FRAME_LATENCY = 2`, safe outside `Scratch` retries); `host/ink/src/device/wgpu/present.rs:250-258` and `host/ink/src/device/metal/present.rs:171-180` explicitly wait on each slot's previous GPU submission/command buffer before reusing it.

**Suggested fix and regression test.** Either size `FrameUniform::RING` strictly above the worst-case in-flight depth (e.g., at least `FRAME_LATENCY + 2` on Android, or track per-slot `wgpu::SubmissionIndex` / `on_submitted_work_done` completion flags and wait/fallback to `queue.write_buffer` when a slot is still in flight — which also handles drivers returning extra swapchain images and unbounded `Scratch` retries). Add a regression test in `gpu/tests/it/uniform.rs` asserting `FrameUniform::slots()` exceeds `FRAME_LATENCY + 1` (or exercising >4 back-to-back submissions without waiting on a swapchain acquire, verifying each submission reads its own uniform bytes).

### Siblings checked

Checked gpu/src/buffers.rs:32 + gpu/src/frame.rs:398-415 (IN_FLIGHT = 3 via on_submitted_work_done, safe for RING = 4), gpu/src/window.rs:84 (latency 2), vendor/wgpu-hal/src/metal/surface.rs:336 (maximumDrawableCount = 3, safe outside Scratch retries), host/ink/src/device/wgpu/present.rs:250-258 (explicit SubmissionIndex poll per ring slot), host/ink/src/device/metal/present.rs:171-180 (explicit MTLCommandBuffer waitUntilCompleted per slot), and packages/shader/rust/src/lib.rs:256-293 (does not write FrameUniform while !drawable).
