```prompt Call Java from my GPU module on Android
Give the GPU module of the Exact app in this folder Android's Java VM and `Context` before its first request, so that its crates can call into Java. Use https://github.com/expo/exact/blob/main/docs/recipes/gpu-module-android.md as the source for each step. The Exact checkout has the same page at docs/recipes/gpu-module-android.md.

1. If this folder is not an Exact app (it has no exact.mjs and app.contract), stop and tell me. If the app has no GPU module (no `gpu/` folder beside app.json), stop and tell me: the gpu-module recipe adds one.
2. If I did not say which crate or Java API needs the VM or the `Context` (HTTP through `HttpURLConnection`, the app's `AssetManager`, a crate that reads `ndk-context`), ask me before you write code. If Android is not one of the app's targets, tell me.
3. In the module's Rust, add one `exact_gpu::android_init!` line beside `module!`, as the recipe shows. Its closure gets `android`, which holds `vm`, `env` and `context`, and returns a `Result` whose error is `Display`. Compose several initializers with `?`.
4. Give each initializer what it needs. `env` is valid for this call only: do not keep it. `context` is valid on every attached thread for the life of the process. Use `vm` to attach a thread that the module starts. For a crate that reads `ndk-context`, call `ndk_context::initialize_android_context(android.vm, android.context)`.
5. Do not rely on `JNI_OnLoad`: Android opens the module with `dlopen`, which does not run it. Bind a Java class's `native` methods with `RegisterNatives`. Load an app's own class through `context.getClassLoader()`, because `FindClass` can see only the system class loader there.
6. Put no `cfg` on the line: on every other platform, the web included, it compiles to nothing. Return each error and leave no Java exception pending: either one refuses the module, and its canvases stay unpainted.
7. Follow the platform checks in docs/start-here.md (`bun exact.mjs docs platform checks`) for the targets in the app's AGENTS.md and app.json until they pass. Read the reports, including counted findings; a zero exit code alone does not mean clean. Fix the app, not the test. On Android, a log line with `Android initialization failed:` and the error means that the module was refused. If a finding stays after three rounds of fixes, or the app had it before you changed anything, record it (step 8) and report it; do not keep trying.
8. When a doc was wrong or missing, or a step needed a workaround, read `bun exact.mjs feedback status`. Under `never`, keep no note. Otherwise record it: `bun exact.mjs feedback note "<what happened>"`, which goes to Expo only as that status says. Do not change the policy; tell me how many notes you kept.
9. Tell me which initializers the line runs, what the checks reported on Android and on each other target, and what stays untested if no Android device or emulator was available.
```
